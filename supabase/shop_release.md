# B안 운영 적용

1. Supabase SQL Editor에서 shop_preflight.sql과 shop_postcheck.sql을 조회하고 결과를 보관한다. postcheck는 적용 전에도 사용할 수 있다. 운영 백업의 복구 가능 시점을 확인한다. 기존 공부 기록 및 그룹을 개별 수정하지 않는다.
2. 운영 fact 테이블이 확정된 순공 세션만 담는지, 시작/종료 밀리초와 휴지통 상태가 원본 수정·복구 시 갱신되는지 확인한다. authenticated/anon 역할이 facts를 직접 수정할 수 없어야 한다. 기존 DB에 이름이 같은 상점 객체가 있으면 먼저 정의를 비교한다.
3. 승인 후 migrations/013_shop.sql 하나를 SQL Editor에서 실행한다. 초기 적립 규칙은 없으며 상품 가격은 비어 있다. 기본 칭호·스킨·테마는 모든 계정에 기본값으로 제공한다. 기존 데이터에 대한 일괄 업데이트는 없다. shop_postcheck.sql로 기존 수치와 트리거 상태를 확인한다. 운영 중 새 기록이 추가된 경우 시점 차이를 고려한다.
4. GitHub 변경사항을 검토하고 배포한다. 권한이 다른 테스트 계정으로 관리자 설정, 구매, 칭호 장착, 친구/그룹 표시 및 06시 경계 정산을 확인한다. 테스트용 운영 변경은 별도 승인을 받는다.
5. 관리자 → 크레딧/상점 관리에서 회원을 선택한다. 상품명·가격·진열과 적립 설정은 서비스 전체에 적용된다. 지급과 회수는 선택한 회원에게만 적용된다. 요율과 가격이 결정되기 전에는 기본 상태로 둔다.
6. 문제가 생기면 GitHub에서 이번 커밋을 revert하고 재배포한다. 적립이 이미 활성화되었고 즉시 정지가 필요하면 DB 관리자가 새 트리거만 비활성화한다. ALTER TABLE public.study_session_facts DISABLE TRIGGER chageun_shop_settlement; 원장과 기존 기록은 유지한다. 정지 구간의 재정산을 검토한 뒤 재개한다.
7. 기존 채팅 만료 작업은 전용 작업인지 shop_preflight 결과로 확인한다. 맞으면 Supabase Cron에서 chageun-group-chat-expiry 작업만 비활성화한다. 공부 기록 정리와 알림 보존 작업은 계속 실행한다.
